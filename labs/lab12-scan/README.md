# lab12 — 스캔 (Kogge-Stone)

**목표:** 경쟁 상태가 실제로 어떤 결과를 내는지 관찰하고, 스캔 커널의 세 판본이
각각 무엇을 아끼는지 코드로 따져 본다.

`scan.cu` 하나에 커널 다섯 개가 들어 있다. 두 개는 완성 상태로 제공되고,
나머지 세 개를 차례로 채운다.

## 이 커널들은 블록 안에서만 스캔한다

슬라이드의 커널은 자기 블록 구간만 스캔하고, 그 구간의 합을
`partialSums[blockIdx.x]`에 남긴다. 전체 배열을 스캔하려면 세 단계가 필요하다.

1. 블록별 스캔 — 슬라이드의 커널
2. `partialSums` 스캔
3. 각 블록에 앞선 블록들의 합 더하기

**2단계와 3단계는 슬라이드에 없다.** 그래서 호스트 코드와 함께 완성 상태로
제공한다. 여러분이 채우는 것은 1단계 커널의 본체뿐이다.
2단계를 블록 하나로 끝내려고 `N`을 `BLOCK_DIM x BLOCK_DIM` 이하로 제한한다.

마지막 열은 재는 것이 아니라 **소스를 읽고 세는 것이다.** 세 커널의 루프
본문을 나란히 놓고 `__syncthreads()`가 몇 번 나오는지 센다.

> **시간 열은 참고용이다. 세 값의 순서로 무엇을 결론짓지 마라.**
> `N`이 작아서 세 커널의 차이가 측정 잡음과 비슷한 크기다. 카드에 따라
> 순서가 그대로 뒤집힌다. **결과가 예상과 달라도 여러분의 구현이 잘못된 것이
> 아니다. 측정값을 그대로 기록하라.**
> 이 랩에서 확실하게 재현되는 것은 1절의 경쟁 상태와 각 커널의 정확성이다.

## 4. exclusive 채우기 — 도전 과제

`scan_exclusive_kernel`의 적재 부분을 채운다. 슬라이드 17이다.
루프와 마무리는 `double` 커널과 완전히 같다. 다른 곳은 처음 적재뿐이다.
inclusive는 자기 값까지 더하고 exclusive는 자기 앞까지만 더한다.

## 빌드와 실행

```
make            # scan 을 빌드한다
make run        # ./scan 1048576 과 같다
make test       # verify.py 로 자체 점검한다
make clean
make help
```

인자는 `./scan <N>` 형태이고, 생략하면 `1048576`(1<<20)이다.
`N`은 `BLOCK_DIM`(1024)의 배수여야 하고 `1048576` 이하여야 한다.
조건에 맞지 않으면 프로그램이 실행 전에 막는다.

시간은 커널마다 1000회 반복한 평균이다. `N`이 작아 1회 측정은 흔들린다.

**왼쪽 시간은 1단계 커널만 잰 것이다.** 괄호 안이 3단계 전체다.
2, 3단계는 다섯 버전이 완전히 같은 코드를 쓰므로, 전체를 재면 그 공통 부분이
시간의 상당 부분을 차지해서 정작 비교하려는 1단계의 차이가 묻힌다.

## 검증

```
make test
```

`verify.py`는 **shared 커널만** 판정한다. `race`는 틀리는 것이 정상이고,
`double`은 완성 제공된 것이며, `exclusive`는 선택 과제다.

CPU 참조는 `double`로 누적한다. `float`로 누적하면 뒤로 갈수록 참조 자신이
어긋나서 기준 구실을 못 한다. 리덕션 랩에서 확인한 것과 같은 이유다.
비교는 배열 전체의 대표 크기 대비 상대오차 1e-3까지 통과로 친다.

## 토론 문제

**1.** `race` 커널에는 `__syncthreads()`가 루프 끝에 분명히 있다.
그런데도 결과가 틀리고, 틀리는 위치가 실행할 때마다 달라진다.
루프 한 번 안에서 어떤 스레드가 무엇을 읽고 무엇을 쓰는지 적어 보라.
`output[i - stride]`를 읽는 스레드와 `output[i]`에 쓰는 스레드가 각각 누구인가?
그 둘 사이에 기다리는 지점이 있는가?

**2.** 세 커널(`global`, `shared`, `double`)이 무엇이 다른지 두 가지 축으로
나눠서 적어라. **시간이 아니라 코드를 근거로 답한다.**

- 데이터를 어디에 두는가 (전역 메모리 / 공유 메모리)
- 루프 한 번에 `__syncthreads()`를 몇 번 부르는가. 3절 표의 마지막 열이다

`double`이 버퍼를 두 장 쓰면 `__syncthreads()`를 한 번 줄일 수 있는 이유는
무엇인가? 한 장으로 하려면 왜 두 번이 필요한가?
읽는 자리와 쓰는 자리가 겹치는지를 따져 보면 답이 나온다.

그리고 **두 축이 각각 무엇을 아껴 주는지** 적어라. 공유 메모리는 무엇을
아끼고, `__syncthreads()`를 줄이는 것은 무엇을 아끼는가?
둘 중 어느 쪽이 이 크기에서 더 크게 작용할지는 재 봐야 알고,
카드가 바뀌면 답도 바뀐다. 그러니 여기서는 **무엇을 아끼는가**까지만 답한다.

**2-1.** 왼쪽(1단계)과 괄호 안(전체)의 차이를 보라.
2, 3단계가 전체에서 차지하는 몫은 얼마인가?
1단계만 아무리 최적화해도 전체가 그만큼 빨라지지 않는 이유를 설명하라.

**3.** 이 커널들은 블록 안에서만 스캔한다.
전체 배열을 스캔하려면 무엇이 더 필요한가?
`scan.cu`의 호스트 코드를 읽고, 세 단계가 각각 무엇을 하는지 적어 보라.
`N`을 `BLOCK_DIM x BLOCK_DIM` 이하로 제한한 이유는 무엇인가?
