# lab13 — 3D stencil

**목표:** 3D stencil 의 최적화 4단계를 측정하고, 공유 메모리 사용량이
점유율과 어떻게 연결되는지 확인한다.

마지막 실습이다. 이번 학기에 쌓은 것이 한자리에 모인다.
타일링(lab06), coarsening(lab07), occupancy(lab04), 그리고 여기서 처음
이름이 붙는 **register tiling** 이다.

3D 인덱싱도 여기서 처음 나온다. `in[i*N*N + j*N + k]` 다.
lab01 에서 `A[row*N + col]` 을 손으로 풀어 본 것이 2차원이었다면
이번에는 한 축이 더 붙었을 뿐이다.

## 커널 네 개

| 단계 | 슬라이드 | 공유 메모리 | 상태 |
|---|---|---|---|
| basic | 8 | 없음 | 완성 제공 |
| tiled | 17 | 3D 타일 한 장 `in_s[T][T][T]` | 완성 제공 |
| coarse | 31 | 2D 타일 **세 장** | 완성 제공 |
| register | 32 | 2D 타일 **한 장** + 레지스터 2개 | **여기를 채운다** |

3단계까지는 완성되어 있다. 채울 곳은 `stencil_register_kernel` 하나뿐이다.

## 1. 네 커널을 비교한다

```
make
./sweep.sh all
```

| 커널 | ms | GB/s | 공유메모리/블록 | SM당 블록 | 공유MEM 한계 |
|---|---|---|---|---|---|
| basic | | | | | |
| tiled | | | | | |
| coarse | | | | | |
| register | | | | | |

`register` 는 아직 `(미구현)` 으로 나온다. 3절에서 채운 뒤 다시 채워 넣는다.

유효 대역폭은 `2 * N^3 * 4바이트 / 시간` 이다. 원소 하나를 한 번 읽고
한 번 쓴다고 보는 **최소 트래픽 기준**이라, 겹쳐 읽는 것이 많은 버전일수록
이 값이 낮게 나온다. 그것이 의도한 동작이다.

`N=256` 이면 배열 하나가 64MB, 입출력 합계 128MB 다. L2 를 넘겨야
캐시가 아니라 메모리를 재게 된다. 프로그램이 첫 줄에 이 값을 찍어 준다.

### 두 열의 차이를 눈여겨보라

- **SM당 블록** — 실제로 SM 하나에 올라가는 블록 수다
- **공유MEM 한계** — 공유 메모리만 따졌을 때 들어갈 수 있는 블록 수다

둘이 같으면 공유 메모리가 한계다. 다르면 다른 것이 먼저 막고 있다는 뜻이다.
어느 쪽인지가 토론 문제 2번이다.

## 2. IN_TILE_DIM 을 바꿔 본다

```
./sweep.sh tile
```

3D 타일링(2단계)의 `IN_TILE_DIM` 만 바꾼다. 이 값은 공유 메모리 배열의
크기라 컴파일 시점에 박히므로, 스크립트가 값마다 다시 빌드한다.

| IN_TILE_DIM | OUT_TILE_DIM | 스레드/블록 | ms | GB/s | 공유메모리 |
|---|---|---|---|---|---|
| 6 | 4 | 216 | | | |
| 8 | 6 | 512 | | | |
| 10 | 8 | 1000 | | | |
| 12 | 10 | 1728 | | | |

**12 는 실패한다. 그것이 정상이다.**
왜 실패하는지 직접 계산해 보라. 블록이 3D 이므로 스레드 수는
`IN_TILE_DIM^3` 이고, 블록 하나에 올릴 수 있는 스레드에는 상한이 있다.
lab04 에서 확인한 그 값이다. 실패 메시지에 두 숫자가 다 나오니 대조해 보라.
슬라이드 19~22 가 말하는 "Limits Exceeded" 가 이것이다.

`OUT_TILE_DIM` 은 `IN_TILE_DIM - 2` 다. 블록이 만드는 출력은
`OUT_TILE_DIM^3` 인데 스레드는 `IN_TILE_DIM^3` 개 있다.
`IN_TILE_DIM=6` 이면 216개 스레드가 64개 출력만 만든다.
이 비율이 표의 GB/s 열과 어떻게 이어지는지 보라.

## 3. register tiling 채우기

`stencil.cu` 의 `stencil_register_kernel` 을 채운다.
**지금 그 자리에 들어 있는 것은 3단계(슬라이드 31)와 똑같은 코드다.**
그래서 지금도 결과는 맞게 나온다. 다만 공유 메모리를 세 장 쓴다.

과제는 이것을 슬라이드 32 로 바꾸는 것이다.
**두 슬라이드를 나란히 놓고 다른 곳만 고치면 된다.** 네 군데다.
3D 인덱싱과 경계 검사는 건드리지 않는다.

생각의 요점은 이렇다. `inPrev_s` 와 `inNext_s` 는 스레드가 자기 자리
`[threadIdx.y][threadIdx.x]` 하나만 읽는다. **옆 스레드의 값을 볼 일이 없다.**
그렇다면 그 두 장은 공유 메모리에 있을 이유가 없다.
각자 레지스터에 들고 있으면 된다.

`inCurr_s` 는 다르다. `C1`~`C4` 항이 옆자리를 읽으므로 공유 메모리로 남아야 한다.

채운 뒤 확인한다.

```
make
./stencil 256
make test
```

제대로 고쳤으면 `공유메모리/블록` 이 세 장에서 한 장으로 줄어든다.
줄지 않았으면 `(미구현)` 으로 표시되므로 바로 알 수 있다.

1절 표의 `register` 줄을 채워 넣는다.

## 빌드와 실행

```
make            # stencil 을 빌드한다
make TILE=10    # 3D 타일링의 IN_TILE_DIM 을 10으로 두고 다시 빌드한다
make run        # ./stencil 256 과 같다
make test       # verify.py 로 자체 점검한다
make clean
make help
```

인자는 `./stencil <N>` 형태이고, 생략하면 `256` 이다.
`N` 은 8 이상 384 이하다. 384 면 배열 하나가 216MB 라 VRAM 8GB 에서
두 개를 잡는 것이 한계다.

`IN_TILE_DIM` 은 실행 인자가 아니다. 빌드할 때 정해진다.

## 검증

```
make test
```

`verify.py` 는 **register 커널만** 판정한다. 앞의 세 단계는 완성 제공된 것이라
판정 대상이 아니다. 판정 기준은 두 가지다.

1. 공유 메모리가 `coarse` 보다 줄었는가 — 레지스터로 옮겼는지
2. 결과가 CPU 참조와 일치하는가 — 옮기면서 망가뜨리지 않았는지

CPU 참조는 `double` 로 누적한다. `float` 로 일곱 항을 더하면 참조 자신이
흔들려 기준 구실을 못 한다. 리덕션 랩에서 확인한 것과 같은 이유다.

경계(`i`, `j`, `k` 가 0 또는 `N-1`)는 커널이 아예 쓰지 않는 자리다.
그래서 비교에서도 뺀다. 내부 `(N-2)^3` 개만 대조한다.
부동소수점 덧셈 순서가 달라 값이 미세하게 어긋나는 것은 정상이므로,
전체의 대표 크기 대비 상대오차 1e-3까지는 통과로 친다.

## 토론 문제

**1.** `basic` 에서 `tiled` 로 갈 때 전역 메모리 접근이 얼마나 줄어드는가?
7점 stencil 에서 입력 한 원소가 몇 개의 출력에 쓰이는지 세어 보라.

그런데 표를 보면 `tiled` 가 `basic` 보다 **빠르지 않을 수 있다.**
그렇다면 타일링이 아낀 것은 무엇이고, 대신 치른 값은 무엇인가?
`IN_TILE_DIM=8` 이면 512개 스레드가 `OUT_TILE_DIM=6`, 즉 216개 출력만 만든다.
**나머지 스레드는 적재만 하고 계산은 하지 않는다.** 그 비율을 계산해 보라.
2절 표의 `IN_TILE_DIM` 별 GB/s 와 함께 놓으면 더 잘 보인다.

**2.** `coarse` 는 공유 메모리를 세 장 쓰고 `register` 는 한 장이다.
그런데 1절 표의 **SM당 블록** 은 둘이 같게 나온다.
`공유MEM 한계` 열과 나란히 놓고, **무엇이 먼저 막고 있는지** 밝혀라.

블록당 스레드 수와 SM당 최대 스레드 수는 프로그램이 표 아래에 찍어 준다.
lab04 에서 만든 occupancy 표를 같이 펴 놓고 보라.
공유 메모리를 3분의 1로 줄였는데도 SM당 블록이 안 늘어난다면,
register tiling 이 실제로 벌어 준 것은 무엇인가? 표의 시간 열을 보라.

**3.** `inPrev` 와 `inNext` 는 스레드마다 따로 갖는 레지스터다.
공유 메모리처럼 여럿이 나눠 쓰는 것이 아니다.
**그런데도 "타일" 이라고 부르는 이유는 무엇인가?**
블록 전체의 레지스터를 한꺼번에 놓고 보면 무엇이 되는지 생각해 보라.

**4.** lab07 에서 만든 coarsened 행렬곱을 다시 펴 보라.
스레드마다 `float sum[COARSE_FACTOR];` 배열을 하나씩 들고 있었다.
**그것도 register tiling 이었는가?** 그렇게 볼 수 있는 근거와
이번 커널과 다른 점을 함께 적어라.
