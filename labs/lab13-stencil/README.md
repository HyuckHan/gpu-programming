# lab13 — 3D stencil

**목표:** 3D stencil 의 최적화 4단계를 측정하고, **왜 이 최적화들이
효과를 내지 못하는지** 밝힌다.

마지막 실습이다. 이번 학기에 쌓은 것이 한자리에 모인다.
타일링(lab06), coarsening(lab07), occupancy(lab04), 그리고 여기서 처음
이름이 붙는 **register tiling** 이다.

그런데 이번에는 지금까지와 다르다. **최적화를 해도 빨라지지 않는다.**
그것이 오늘의 관찰 대상이다.

3D 인덱싱도 여기서 처음 나온다. `in[i*N*N + j*N + k]` 다.
lab01 에서 `A[row*N + col]` 을 손으로 풀어 본 것이 2차원이었다면
이번에는 한 축이 더 붙었을 뿐이다.

## 커널 네 개

| 단계 | 슬라이드 | 공유 메모리 | 상태 |
|---|---|---|---|
| basic | 8 | 없음 | 완성 제공 |
| tiled | 17 | 3D 타일 한 장 `in_s[T][T][T]` | 완성 제공 |
| coarse | 31 | 2D 타일 **세 장** | 완성 제공 |
| register | 32 | 2D 타일 **한 장** + 레지스터 2개 | **여기를 채운다** |

3단계까지는 완성되어 있다. 채울 곳은 `stencil_register_kernel` 하나뿐이다.

## 1. 네 커널을 비교한다

```
make
./sweep.sh all
```

| 커널 | ms | GB/s | 이론대비 | 공유메모리/블록 | SM당 블록 | 공유MEM 한계 |
|---|---|---|---|---|---|---|
| basic | | | | | | |
| tiled | | | | | | |
| coarse | | | | | | |
| register | | | | | | |

`register` 는 아직 `(미구현)` 으로 나온다. 3절에서 채운 뒤 다시 채워 넣는다.

> **먼저 알아 둘 것.** 이 랩은 지금까지의 랩과 다르다. 사다리를 올라가도
> 성능이 올라가지 않는다. 오히려 아무 최적화도 하지 않은 `basic` 이 가장
> 빠르게 나온다. **그 이유를 찾는 것이 오늘의 과제다.**
>
> **결과를 그대로 기록하라. 느리게 나와도 여러분의 구현이 잘못된 것이 아니다.**
> 뒤집힌 결과가 이 실습의 정답이다.

**`이론대비` 열을 가장 먼저 보라.** 프로그램이 실행 중인 GPU 에 이론 대역폭을
물어보고 각 커널이 그 몇 %에 닿았는지 찍는다. `basic` 이 몇 %에 가 있는가?
남은 여지가 얼마인가? 그 위에 무엇을 얹을 수 있겠는가.

유효 대역폭은 `2 * N^3 * 4바이트 / 시간` 이다. 원소 하나를 한 번 읽고
한 번 쓴다고 보는 **최소 트래픽 기준**이라, 겹쳐 읽는 것이 많은 버전일수록
이 값이 낮게 나온다. 그것이 의도한 동작이다.

`N=256` 이면 배열 하나가 64MB, 입출력 합계 128MB 다. L2 를 넘겨야
캐시가 아니라 메모리를 재게 된다. 프로그램이 첫 줄에 이 값을 찍어 준다.

## 두 열의 차이를 눈여겨보라

- **SM당 블록** — 실제로 SM 하나에 올라가는 블록 수다
- **공유MEM 한계** — 공유 메모리만 따졌을 때 들어갈 수 있는 블록 수다

둘이 같으면 공유 메모리가 한계다. 다르면 다른 것이 먼저 막고 있다는 뜻이다.
어느 쪽인지가 토론 문제 2번이다.

## 2. IN_TILE_DIM 을 바꿔 본다

```
./sweep.sh tile
```

3D 타일링(2단계)의 `IN_TILE_DIM` 만 바꾼다. 이 값은 공유 메모리 배열의
크기라 컴파일 시점에 박히므로, 스크립트가 값마다 다시 빌드한다.

| IN_TILE_DIM | OUT_TILE_DIM | 스레드/블록 | ms | GB/s | 공유메모리 |
|---|---|---|---|---|---|
| 6 | 4 | 216 | | | |
| 8 | 6 | 512 | | | |
| 10 | 8 | 1000 | | | |
| 12 | 10 | 1728 | | | |

**12 는 실패한다. 그것이 정상이다.**
왜 실패하는지 직접 계산해 보라. 블록이 3D 이므로 스레드 수는
`IN_TILE_DIM^3` 이고, 블록 하나에 올릴 수 있는 스레드에는 상한이 있다.
lab04 에서 확인한 그 값이다. 실패 메시지에 두 숫자가 다 나오니 대조해 보라.
슬라이드 19~22 가 말하는 "Limits Exceeded" 가 이것이다.

`OUT_TILE_DIM` 은 `IN_TILE_DIM - 2` 다. 블록이 만드는 출력은
`OUT_TILE_DIM^3` 인데 스레드는 `IN_TILE_DIM^3` 개 있다.
`IN_TILE_DIM=6` 이면 216개 스레드가 64개 출력만 만든다.
이 비율이 표의 GB/s 열과 어떻게 이어지는지 보라.

## 3. register tiling 채우기

`stencil.cu` 의 `stencil_register_kernel` 을 채운다.
**지금 그 자리에 들어 있는 것은 3단계(슬라이드 31)와 똑같은 코드다.**
그래서 지금도 결과는 맞게 나온다. 다만 공유 메모리를 세 장 쓴다.

과제는 이것을 슬라이드 32 로 바꾸는 것이다.
**두 슬라이드를 나란히 놓고 다른 곳만 고치면 된다.** 네 군데다.
3D 인덱싱과 경계 검사는 건드리지 않는다.

생각의 요점은 이렇다. `inPrev_s` 와 `inNext_s` 는 스레드가 자기 자리
`[threadIdx.y][threadIdx.x]` 하나만 읽는다. **옆 스레드의 값을 볼 일이 없다.**
그렇다면 그 두 장은 공유 메모리에 있을 이유가 없다.
각자 레지스터에 들고 있으면 된다.

`inCurr_s` 는 다르다. `C1`~`C4` 항이 옆자리를 읽으므로 공유 메모리로 남아야 한다.

채운 뒤 확인한다.

```
make
./stencil 256
make test
```

제대로 고쳤으면 `공유메모리/블록` 이 세 장에서 한 장으로 줄어든다.
줄지 않았으면 `(미구현)` 으로 표시되므로 바로 알 수 있다.

공유 메모리가 3분의 1이 되었으니 `SM당 블록` 도 늘었는가? **표에서 확인하라.**
`coarse` 줄과 비교해 보면 된다. 늘지 않았다면 왜 그런지가 토론 문제 3번이다.
성능도 극적으로 좋아지지는 않는다. 그것이 정상이다.
이 과제의 목적은 성능을 얻는 것이 아니라 기법을 손으로 한 번 써 보는 것이다.
register tiling 은 12개 덱을 통틀어 여기에만 나온다.

1절 표의 `register` 줄을 채워 넣는다.

## 빌드와 실행

```
make            # stencil 을 빌드한다
make TILE=10    # 3D 타일링의 IN_TILE_DIM 을 10으로 두고 다시 빌드한다
make run        # ./stencil 256 과 같다
make test       # verify.py 로 자체 점검한다
make clean
make help
```

인자는 `./stencil <N>` 형태이고, 생략하면 `256` 이다.
`N` 은 8 이상 384 이하다. 384 면 배열 하나가 216MB 라 VRAM 8GB 에서
두 개를 잡는 것이 한계다.

`IN_TILE_DIM` 은 실행 인자가 아니다. 빌드할 때 정해진다.

## 검증

```
make test
```

`verify.py` 는 **register 커널만** 판정한다. 앞의 세 단계는 완성 제공된 것이라
판정 대상이 아니다. 판정 기준은 두 가지다.

1. 공유 메모리가 `coarse` 보다 줄었는가 — 레지스터로 옮겼는지
2. 결과가 CPU 참조와 일치하는가 — 옮기면서 망가뜨리지 않았는지

CPU 참조는 `double` 로 누적한다. `float` 로 일곱 항을 더하면 참조 자신이
흔들려 기준 구실을 못 한다. 리덕션 랩에서 확인한 것과 같은 이유다.

경계(`i`, `j`, `k` 가 0 또는 `N-1`)는 커널이 아예 쓰지 않는 자리다.
그래서 비교에서도 뺀다. 내부 `(N-2)^3` 개만 대조한다.
부동소수점 덧셈 순서가 달라 값이 미세하게 어긋나는 것은 정상이므로,
전체의 대표 크기 대비 상대오차 1e-3까지는 통과로 친다.

## 토론 문제

**1.** `basic` 은 이론 대역폭의 몇 %에 도달했는가? 1절 표의 `이론대비` 열이다.
그 상태에서 공유 메모리 타일링으로 **더 빨라질 수 있는가?**
빨라질 수 있다면 무엇을 줄여서 그렇게 되는 것인지, 없다면 왜 없는지 적어라.

**2.** `tiled` 는 `IN_TILE_DIM=8` 일 때 512개 스레드가 `OUT_TILE_DIM=6`,
즉 216개 출력만 만든다. **나머지 스레드는 무엇을 하는가?**
그 비율을 계산하고, 그것이 1절 표의 시간과 GB/s 에 어떻게 나타나는지 적어라.
2절 표에서 `IN_TILE_DIM` 을 6, 8, 10 으로 바꿨을 때 이 비율이 어떻게 변하는지
함께 보면 더 잘 보인다.

**3.** `register` 는 공유 메모리를 타일 세 장에서 한 장으로, 3분의 1로 줄였다.
**그런데 `SM당 블록` 은 `coarse` 와 똑같이 나온다.**
`공유MEM 한계` 열은 그보다 훨씬 큰 수를 말하는데도 그렇다.
**무엇이 먼저 한계로 작용하고 있는가?**

프로그램이 표 아래에 블록당 스레드 수와 SM당 최대 스레드 수를 찍어 준다.
lab04 에서 만든 표를 펴 놓고 그 두 숫자로 나눗셈을 해 보라.
occupancy 를 정하는 자원이 하나가 아니라는 것이 요점이다.
공유 메모리를 아무리 줄여도, 먼저 걸리는 것이 따로 있으면 블록 수는 안 늘어난다.

**4.** lab07 에서 만든 coarsened 행렬곱을 다시 펴 보라.
스레드마다 `float sum[COARSE_FACTOR];` 배열을 하나씩 들고 있었다.
**그것도 register tiling 이었는가?** 그렇게 볼 수 있는 근거와
이번 커널과 다른 점을 함께 적어라.

**5.** 교재는 이 최적화들이 큰 효과를 낸다고 설명한다. 오늘 측정에서는
그렇지 않았다. **타일링이 아껴 준 것과, 그 대가로 치른 것을 각각 적어라.**

- 아낀 것 — `basic` 이 원소 하나를 계산할 때 전역 메모리에서 몇 번 읽는가?
  `tiled` 는 같은 값을 몇 번 읽는가?
- 치른 것 — 2번과 3번에서 센 두 가지다. 스레드 낭비와 블록당 스레드 수

7점 스텐실에서 한 원소가 재사용되는 횟수는 최대 몇 번인가?
lab06 의 타일링 행렬곱에서는 한 원소가 몇 번 재사용되었는가?
두 숫자를 견주면, 같은 기법이 한쪽에서는 이득이고 다른 쪽에서는 아닌 이유가
보인다. 아래 "학기를 닫으며" 절이 실마리다.

## 학기를 닫으며 — 최적화에는 대가가 있다

이번 학기에 예상과 다른 결과를 여러 번 만났다.

- **lab07** — 전치에서 `naive 16x16` 이 `naive 32x32` 보다 몇 배 빨랐다.
  소스가 한 글자도 다르지 않고 블록 모양만 달랐다
- **lab08** — `ncu` 로 재 보니 `N=1024` 에서 DRAM 사용률이 거의 0 이었다.
  행렬 세 개가 L2 안에 들어가서 메모리를 건드리지도 않았다
- **lab09** — 상수 메모리와 전역 메모리의 차이가 예상보다 작았다
- **lab13** — 오늘. 타일링을 해도 `basic` 보다 빨라지지 않는다

오늘의 결과에는 분명한 원인이 있다. **타일링과 coarsening 이 전역 접근을
줄여 주는 대신 다른 것을 가져갔다.** 1절 표와 2절 표가 그 대가를 보여 준다.

- **스레드 낭비** — `tiled` 는 블록당 512 스레드로 216 개 출력만 만든다.
  나머지는 테두리를 적재하고 계산에는 참여하지 않는다.
  출력 하나를 만드는 데 드는 스레드가 `basic` 보다 훨씬 많다
- **블록당 스레드 수** — `coarse` 와 `register` 는 블록당 1024 스레드다.
  SM 당 최대 스레드 수를 그 값으로 나눠 보라. SM 하나에 블록이 몇 개
  올라가는가? `basic` 은 512 스레드라 몇 개가 올라가는가?
  `공유MEM 한계` 열이 훨씬 큰 수를 말하는데도 실제 블록 수가 늘지 않는
  이유가 여기에 있다

즉 공유 메모리를 아무리 아껴도 먼저 걸리는 것이 따로 있었고, 그 대가로 치른
스레드 낭비와 낮은 블록 수가 전역 접근을 줄여 얻은 이득보다 컸다.
`basic` 은 그 대가를 하나도 치르지 않는다. 경계 검사 하나로 원소당 스레드
하나씩 쓰고 끝이다.

**교재의 최적화 기법이 무의미하다는 뜻이 아니다.** 그 기법이 이득이 되려면
아껴서 얻는 것이 대가보다 커야 한다는 뜻이다. 7점 스텐실은 한 원소를 일곱 번
재사용하는 것이 전부라 아끼는 쪽이 작다. 재사용이 훨씬 많은 행렬곱(lab06,
한 원소를 `TILE_DIM` 번 재사용)에서는 `TILE_DIM` 을 잘 잡으면 이득이 남았다.
잘못 잡으면 거기서도 남지 않았다. 여러분의 lab06 표에서 확인할 수 있다.

lab07 의 전치는 또 다른 경우다. 거기서 문제는 재사용이 아니라 쓰기 주소가
흩어지는 것이었고, 공유 메모리를 들이지 않고 블록 모양만 바꾸는 것으로도
상당 부분 해결됐다. **문제가 무엇인지 먼저 알아야 어떤 기법을 쓸지 정할 수
있다.** 아무 데나 타일링을 얹는 것이 최적화가 아니다.

그래서 오늘 배운 것은 "타일링은 소용없다" 가 아니라 이것이다.
**최적화를 배웠으면 그것이 무엇을 아끼고 무엇을 대가로 치르는지 함께 알아야
하고, 어느 쪽이 큰지는 짐작이 아니라 측정으로 판단한다.**
이번 학기에 `verify.py` 와 `ncu` 를 계속 돌린 이유가 그것이다.
