# lab06 — 공유 메모리 타일링 행렬곱

**목표:** naive 행렬곱을 공유 메모리 타일링으로 바꿔 전역 메모리 접근 횟수를 TILE_DIM분의 1로 줄인다.

## 과제

`skeleton.cu`의 `mm_tiled_kernel` 본체를 채운다. 채울 곳은 그곳 하나뿐이고,
naive 커널(`mm_kernel`, lab05 에서 직접 만들었다)과 호스트 코드는 이미 완성되어 있다.
shared memory 선언 두 줄도 그대로 두면 된다.

5장 슬라이드의 타일링 코드를 그대로 옮기면 된다. 변수명(`A_s`, `B_s`, `row`,
`col`, `sum`, `tile`, `i`)도 슬라이드와 같게 유지하라.

> 슬라이드에서는 A가 N×N, B가 N×K인 직사각 행렬이라 B와 C의 인덱스에 `K`가
> 쓰였다. 이 실습은 **정사각 행렬(N×N)로 단순화**했으므로 `K` 자리에 전부 `N`을
> 넣는다. 또한 N이 TILE_DIM의 배수인 경우만 다루므로 경계 검사는 필요 없다
> (배수가 아니면 프로그램이 실행 전에 막는다).

## 빌드와 실행

```
make                     # skeleton.cu 를 matmul 로 빌드
make broken_syncthreads  # 관찰 과제용. 필요할 때 따로 빌드한다
make run                 # ./matmul 4096 16 과 같다
make help                # 쓸 수 있는 명령과 인자를 모두 보여준다
```

인자는 `./matmul <N> <TILE_DIM>` 형태다. TILE_DIM은 8, 16, 32 중 하나이고
N은 TILE_DIM의 배수여야 한다. 인자를 생략하면 N=4096, TILE_DIM=16이다.

```
./matmul 4096 16      # 기본 조건. 행렬 3개 201MB — L2 를 한참 넘는다
./matmul 1024 16      # 행렬 3개 12MB — L2 에 다 들어간다
./matmul 4096 32      # 블록당 1024 스레드. occupancy 는 낮아지는데 속도는?
```

`make run N=1024 TILE=16` 처럼 Makefile 변수로 넘겨도 된다.
nvcc 플래그는 Makefile이 관리하므로 직접 칠 일은 없다.

## 검증

```
make test       # python3 verify.py 와 같다
```

기준선 naive 는 `TILE_DIM` 을 바꿔도 **항상 16x16 블록으로 고정**해서 측정한다.
기준선까지 같이 흔들리면 배속이라는 숫자를 해석할 수 없기 때문이다.
그래서 `N` 은 16의 배수이기도 해야 한다.

`verify.py`가 빌드부터 네 가지 (N, TILE_DIM) 조합 실행까지 자동으로 돌리고
정확성 통과 여부와 배속을 출력한다. 실패하면 짚이는 원인까지 알려 준다.
**제출 전에 반드시 통과시켜라.**

프로그램 자체의 검증은 두 겹이다. tiled 결과를 naive 결과와 대조하고,
N이 1024 이하면 CPU 참조 구현(`mm_cpu`)과도 한 번 더 대조한다.
부동소수점 덧셈 순서가 달라 값이 미세하게 어긋나는 것은 정상이므로,
행렬 전체의 대표 크기 대비 상대오차 1e-3까지는 통과로 친다.

## 관찰 과제 — `broken_syncthreads`

```
./broken_syncthreads 1024 32
```

이 프로그램은 정상 빌드되고 실행도 된다. **여러 번 반복 실행한 뒤**
출력이 어떻게 달라지는지 기록하라. 보고서에 다음을 답한다.

1. 실행할 때마다 결과가 어떻게 달라지는가? 무엇이 같고 무엇이 다른가?
2. 왜 그런 일이 생기는가? 어떤 스레드가 어떤 데이터를 언제 읽어서 문제가 되는가?
3. TILE_DIM을 8, 16, 32로 바꾸면 증상의 정도가 달라지는가? 그 이유는?

## 토론 문제

**1.** `TILE_DIM`을 8, 16, 32로 바꿔 가며 `N=4096`에서 재라.
세 값의 occupancy 는 lab04 에서 만든 표로 계산할 수 있다.
블록당 스레드 수가 64, 256, 1024 이고 SM 당 최대 1536 스레드다.

그런데 **16과 32의 성능은 거의 같게 나온다.** occupancy 는 32 쪽이 뚜렷하게
낮은데도 그렇다. occupancy 가 성능을 결정하는가, 아니면 다른 역할을 하는가?
8이 느린 이유는 16과 32가 비슷한 이유와 같은 것인가, 다른 것인가?

**2.** 두 `N`에서 배속 차이가 나는 이유를 설명하라.
`./matmul 1024 16`은 행렬 3개가 12MB, `./matmul 4096 16`은 201MB다.
이 GPU 의 L2 캐시 크기와 나란히 놓고 보라.
