# lab07 — coalescing과 thread coarsening

**목표:** 문제 크기와 thread coarsening이 행렬곱 성능에 어떤 영향을 주는지 측정한다.

lab05에서 naive를, lab06에서 타일링을 직접 만들었다. 오늘은 그 둘을 기준선으로 두고
한 단계 더 최적화한다. 세 커널 모두 같은 결과를 내야 한다.

성능 비교의 기준선인 naive는 `TILE_DIM`을 바꿔도 **항상 16x16 블록으로 고정**해서
측정한다. 기준선까지 같이 흔들리면 배속이라는 숫자를 해석할 수 없기 때문이다.

## 슬라이드와 다른 점

슬라이드 22는 A가 M×N, B가 N×K인 직사각 표기라 매개변수가 `M`, `N`, `K` 세 개다.
이 실습은 lab05, lab06과 맞춰 **정사각(N×N)으로 단순화**했으므로 `N` 하나만 받는다.
슬라이드에서 `M`과 `K`가 쓰인 자리에 전부 `N`을 넣으면 된다.
이것이 슬라이드와 다른 유일한 지점이고, 소스에도 같은 내용을 주석으로 적어 두었다.

## 1. 크기 스윕

먼저 빌드하고 크기를 바꿔가며 측정한다.

```
make
./sweep.sh size
```

`TILE_DIM=16`, `COARSE_FACTOR=4`로 고정하고 `N`만 바꾼다.
이 시점에는 `coarse` 열이 `-`로 나온다. 아직 TODO를 안 채웠으니 정상이다.

| N | 행렬 3개 크기 | naive GFLOP/s | tiled GFLOP/s | tiled 배속 |
|---|---|---|---|---|
| 512 | 3 MB | | | |
| 1024 | 12 MB | | | |
| 2048 | 48 MB | | | |
| 4096 | 201 MB | | | |
| 8192 | 805 MB | | | |

실습실 PC의 L2 캐시는 24MB다. 위 표의 "행렬 3개 크기"와 견주어 보라.

## 2. TODO 채우기

`matmul.cu`의 `mm_tiled_coarse_kernel` 본체를 채운다. 채울 곳은 그곳 하나뿐이다.
커널 시그니처, `__shared__` 선언, 실행 구성(grid 계산), 검증은 이미 완성되어 있다.

슬라이드 22를 그대로 옮기면 된다. 변수명(`row`, `colStart`, `sum`, `tile`, `c`)도
슬라이드와 같게 유지하라.

핵심은 **A 타일을 `c` 루프 바깥에서 한 번만 적재**하는 것이다.
블록 하나가 가로로 `TILE_DIM * COARSE_FACTOR` 열을 담당하게 되고,
그만큼 A 타일을 다시 읽지 않아도 된다.

채운 뒤 확인한다.

```
make
./matmul 4096 16 4
make test
```

## 3. coarsening 스윕

```
./sweep.sh coarse
```

`N=4096`, `TILE_DIM=16`으로 고정하고 `COARSE_FACTOR`만 바꾼다.

| COARSE_FACTOR | tiled GFLOP/s | coarse GFLOP/s | coarse 배속 |
|---|---|---|---|
| 1 | | | |
| 2 | | | |
| 4 | | | |
| 8 | | | |

표를 다 채운 뒤, 더 큰 값도 직접 돌려 볼 수 있다.
`./matmul 4096 16 16`, `./matmul 4096 16 32` 까지 받는다.

## 빌드와 실행

```
make            # matmul 을 빌드한다
make run        # ./matmul 4096 16 4 과 같다
make test       # verify.py 로 자체 점검한다
make clean
make help       # 쓸 수 있는 명령과 인자를 모두 보여준다
```

인자는 `./matmul <N> <TILE_DIM> <COARSE_FACTOR>` 형태이고, 생략하면 `4096 16 4`다.
`TILE_DIM`은 8, 16, 32 중 하나, `COARSE_FACTOR`는 1, 2, 4, 8, 16, 32 중 하나다.

슬라이드의 커널들에는 경계 검사가 없다. 그래서 `N`은 `TILE_DIM * COARSE_FACTOR`의
배수여야 하고, 기준선 naive가 16x16 고정이므로 16의 배수이기도 해야 한다.
조건에 맞지 않으면 프로그램이 실행 전에 막는다.

## 검증

```
make test
```

`verify.py`는 **coarse 커널만** 판정한다. naive와 tiled는 이미 완성되어 있으므로
판정 대상이 아니다. 프로그램 자체는 세 커널의 결과를 서로 대조하고,
`N`이 1024 이하면 CPU 참조 구현과도 한 번 더 대조한다.

부동소수점 덧셈 순서가 달라 값이 미세하게 어긋나는 것은 정상이므로,
행렬 전체의 대표 크기 대비 상대오차 1e-3까지는 통과로 친다.

## 토론 문제

**1.** `N`이 작을 때와 클 때 tiled의 배속이 다르게 나온다.
무엇이 달라진 것인가? 1절 표의 "행렬 3개 크기"와 L2 캐시 크기를 나란히 놓고 보라.

**2.** `COARSE_FACTOR`를 계속 키우면 계속 빨라지는가? 어디에서 멈추는가?
멈추는 이유는 무엇인가? 스레드 하나가 `sum` 배열을 몇 개 들고 있어야 하는지,
그리고 블록 하나가 몇 개의 열을 맡게 되는지 세어 보면 실마리가 잡힌다.

**3.** naive 커널의 `B[i*N + col]` 접근은 이미 coalesced다.
한 워프의 32개 스레드가 연속된 주소를 읽는다.
그런데도 tiled가 더 빠른 이유는 무엇인가?
같은 데이터를 몇 번씩 읽는지 세어 보라.
