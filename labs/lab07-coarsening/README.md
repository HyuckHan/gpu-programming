# lab07 — coalescing과 thread coarsening

**목표:** 워프가 어떤 주소를 건드리는지(coalescing)와 thread coarsening이
성능에 어떤 영향을 주는지 측정한다.

1절은 **전치**로 coalescing을 본다. 2·3절은 lab05·lab06에서 만든 행렬곱을
이어받아 coarsening을 본다. 두 부분은 서로 다른 프로그램이다.

성능 비교의 기준선인 naive는 `TILE_DIM`을 바꿔도 **항상 고정된 블록 모양으로**
측정한다(전치는 32x32, 행렬곱은 16x16). 기준선까지 같이 흔들리면 배속이라는
숫자를 해석할 수 없기 때문이다.

## 슬라이드와 다른 점

슬라이드 22는 A가 M×N, B가 N×K인 직사각 표기라 매개변수가 `M`, `N`, `K` 세 개다.
이 실습은 lab05, lab06과 맞춰 **정사각(N×N)으로 단순화**했으므로 `N` 하나만 받는다.
슬라이드에서 `M`과 `K`가 쓰인 자리에 전부 `N`을 넣으면 된다.
이것이 슬라이드와 다른 유일한 지점이고, 소스에도 같은 내용을 주석으로 적어 두었다.

## 1. 전치 — coalescing

`transpose.cu`는 **채울 곳이 없다. 전부 완성되어 있다.**
이 절에서 할 일은 측정하고 해석하는 것이다.

행렬곱으로는 coalescing을 볼 수 없다. naive 행렬곱의 `B[i*N + col]`은 이미
연속 접근이고 `A[row*N + i]`는 워프 전체가 같은 값을 읽는 브로드캐스트다.
접근 횟수만 많을 뿐 패턴이 나쁘지 않아 캐시가 상당 부분을 흡수한다.

전치는 다르다. 읽기와 쓰기 중 한쪽은 반드시 stride-N이 된다.

```
make
./transpose 4096 32
./sweep.sh transpose
```

`N=4096`이면 입력 64MB + 출력 64MB = 128MB다. L2 캐시를 넘는 크기여야
캐시가 아니라 메모리를 재게 된다. 프로그램이 첫 줄에 이 값을 찍어 준다.

지표는 GB/s다. 유효 트래픽은 읽기 + 쓰기, 즉 `2 * N * N * 4` 바이트다.

**배속 열의 기준선은 `naive 32x32` 다.** 다섯 줄 모두 그 한 줄에 대한 비율이다.
이 줄이 1.00x 로 고정돼 있다는 것을 기억해 두어라. 토론 3번에서 쓴다.

| 커널 | ms | GB/s | 이론 대비 | 배속 (naive 32x32 대비) |
|---|---|---|---|---|
| naive 32x32 (기준선) | | | | 1.00x |
| naive 16x16 | | | | |
| tiled, TILE_DIM=8 | | | | |
| tiled, TILE_DIM=16 | | | | |
| tiled, TILE_DIM=32 | | | | |

**`naive 32x32`와 `naive 16x16`은 같은 커널이다.** 소스가 한 글자도 다르지 않고
`blockDim`만 다르다. 그런데 값이 몇 배씩 차이 난다. 몇 배인지 표에서 읽어
적어라. 이것이 이 절의 핵심이다.

> **결과가 예상과 달라도 여러분의 구현이 잘못된 것이 아니다.
> 측정값을 그대로 기록하고 설명하라.** 다섯 줄의 순서는 GPU 마다 다르다.
> `transpose.cu` 는 채울 곳이 없는 완성 코드다. 느리게 나온 줄이 있어도
> 그것이 이 카드에서 나온 결과다.

## 2. TODO 채우기

`matmul.cu`의 `mm_tiled_coarse_kernel` 본체를 채운다. 채울 곳은 그곳 하나뿐이다.
커널 시그니처, `__shared__` 선언, 실행 구성(grid 계산), 검증은 이미 완성되어 있다.

슬라이드 22를 그대로 옮기면 된다. 변수명(`row`, `colStart`, `sum`, `tile`, `c`)도
슬라이드와 같게 유지하라.

핵심은 **A 타일을 `c` 루프 바깥에서 한 번만 적재**하는 것이다.
블록 하나가 가로로 `TILE_DIM * COARSE_FACTOR` 열을 담당하게 되고,
그만큼 A 타일을 다시 읽지 않아도 된다.

채운 뒤 확인한다.

```
make
./matmul 4096 16 4
make test
```

## 3. coarsening 스윕

```
./sweep.sh coarse
```

`N=4096`, `TILE_DIM=16`으로 고정하고 `COARSE_FACTOR`만 바꾼다.

| COARSE_FACTOR | tiled GFLOP/s | coarse GFLOP/s | coarse 배속 |
|---|---|---|---|
| 1 | | | |
| 2 | | | |
| 4 | | | |
| 8 | | | |

표를 다 채운 뒤, 더 큰 값도 직접 돌려 볼 수 있다.
`./matmul 4096 16 16`, `./matmul 4096 16 32` 까지 받는다.

## 빌드와 실행

```
make            # matmul 과 transpose 를 빌드한다
make run        # ./matmul 4096 16 4 과 같다
make runt       # ./transpose 4096 16 과 같다
make test       # verify.py 로 자체 점검한다
make clean
make help       # 쓸 수 있는 명령과 인자를 모두 보여준다
```

인자는 `./matmul <N> <TILE_DIM> <COARSE_FACTOR>` 형태이고, 생략하면 `4096 16 4`다.
`TILE_DIM`은 8, 16, 32 중 하나, `COARSE_FACTOR`는 1, 2, 4, 8, 16, 32 중 하나다.

전치는 `./transpose <N> <TILE_DIM>` 형태이고, 생략하면 `4096 32`다.
기준선 naive가 32x32 고정이므로 `N`은 `TILE_DIM`과 32 양쪽의 배수여야 한다.

슬라이드의 커널들에는 경계 검사가 없다. 그래서 `N`은 `TILE_DIM * COARSE_FACTOR`의
배수여야 하고, 기준선 naive가 16x16 고정이므로 16의 배수이기도 해야 한다.
조건에 맞지 않으면 프로그램이 실행 전에 막는다.

## 검증

```
make test
```

`verify.py`는 **coarse 커널만** 판정한다. naive와 tiled는 이미 완성되어 있으므로
판정 대상이 아니다. 프로그램 자체는 세 커널의 결과를 서로 대조하고,
`N`이 1024 이하면 CPU 참조 구현과도 한 번 더 대조한다.

부동소수점 덧셈 순서가 달라 값이 미세하게 어긋나는 것은 정상이므로,
행렬 전체의 대표 크기 대비 상대오차 1e-3까지는 통과로 친다.

## 토론 문제

**1.** naive 전치는 읽기와 쓰기 중 어느 쪽이 문제인가?
`out[col*N + row]`에서 한 워프의 32개 스레드가 접근하는 주소를 실제로 따져 보라.
`threadIdx.x`가 1 늘어나면 주소는 몇 바이트 움직이는가?
그 32개 주소가 캐시 라인 몇 개에 걸치는가?

**2.** `naive 32x32`와 `naive 16x16`은 소스가 같은데도 속도가 다르다.
**어느 쪽이 빨랐는가?** `blockDim`이 워프의 모양을 어떻게 바꾸는지 생각해 보라.
32개 스레드로 이루어진 한 워프가 16x16 블록에서는 몇 개의 행에 걸치는가?
그것이 쓰기 주소의 흩어짐을 어떻게 줄이는가?

**3.** tiled는 공유 메모리를 한 번 더 거친다. 그 비용을 내고도 이득이 있는가?
**무엇과 비교해서 그렇게 판단했는지 먼저 밝혀라.** 1절 표의 배속 열은
`naive 32x32` 를 기준으로 한 값이다. 그런데 표에는 `naive 16x16` 도 있다.

- `tiled` 세 줄 중 가장 빠른 것을 `naive 32x32` 와 비교하면 어느 쪽이 빠른가?
- 같은 것을 `naive 16x16` 과 비교하면 어떻게 되는가?
- 두 비교의 답이 다르다면, "타일링이 이득인가"라는 질문에는 무엇을 덧붙여야
  답이 되는가?

공유 메모리에 들르는 비용과, 그 대가로 전역 메모리에서 아낀 것을 견주어 보라.

**4.** lab06 보고서에서 잰 행렬곱의 naive/tiled 배속과, 1절 전치 표의 배속을
나란히 놓아라. 어느 쪽 차이가 더 큰가? 두 커널의 메모리 접근 패턴이 어떻게
다르기에 차이의 크기가 다른가?

**5.** `COARSE_FACTOR`를 계속 키우면 계속 빨라지는가? 어디에서 멈추는가?
멈추는 이유는 무엇인가? 스레드 하나가 `sum` 배열을 몇 개 들고 있어야 하는지,
그리고 블록 하나가 몇 개의 열을 맡게 되는지 세어 보면 실마리가 잡힌다.
