**목표:** 데이터 경쟁이 실제로 어떤 결과를 내는지 관찰하고, atomic 연산과 privatization의 비용을 측정한다.

`histogram.cu` 하나에 커널 세 개가 들어 있다. 첫 번째는 완성 상태로 제공되고,
나머지 두 개를 차례로 채운다.

## 4. 분포를 바꿔 본다

지금까지는 값이 0~255에 고르게 퍼져 있었다. 이번에는 몇 칸에 몰아 넣는다.

```
./histogram --skewed
```

| 버전 | 균등 (ms) | 치우침 (ms) | 몇 배 |
|---|---|---|---|
| race | | | |
| atomic | | | |
| private | | | |

> **결과가 예상과 달라도 여러분의 구현이 잘못된 것이 아니다.
> 측정값을 그대로 기록하고 설명하라.** 세 버전이 분포에 얼마나 민감한지는
> GPU 마다 다르다. 거의 변하지 않는 줄도 있고 줄어드는 줄도 있다.
> "몇 배" 열을 그대로 채우면 된다.

## 빌드와 실행

```
make            # histogram 을 빌드한다
make run        # ./histogram 67108864 과 같다
make skewed     # ./histogram 67108864 --skewed 과 같다
make test       # verify.py 로 자체 점검한다
make clean
make help
```

인자는 `./histogram <N> [--skewed]` 형태이고, 생략하면 `67108864`(1<<26)이다.
`NUM_BINS`는 256으로 고정이다. 공유 메모리로 1KB뿐이라 여유가 충분하다.

## 검증

```
make test
```

`verify.py`는 **`atomic` 커널만** 판정한다. `race`는 틀리는 것이 정상이라
판정 대상이 아니고, `private`는 선택 과제라 결과만 찍고 판정하지 않는다.
프로그램 자체는 256개 칸을 CPU 참조와 정수 정확일치로 비교한다. 히스토그램은 정수 세기라 허용오차가 없다. 한 칸이라도 다르면 실패다.

합계는 판정과 별개로 항상 찍힌다. 어느 칸이 틀렸는지보다 합계가 먼저 눈에 들어온다.

## 토론 문제

**1.** `race` 버전의 합계가 `N`보다 작게 나온다. 그리고 실행할 때마다 다르다.
사라진 증가 연산은 어디로 갔는가? 두 스레드가 같은 칸을 동시에 1 늘리려 할 때
무슨 일이 일어나는지, 읽고-더하고-쓰는 세 단계로 나눠서 적어 보라.

**2.** `race`와 `atomic`의 코드 차이는 한 줄뿐인데 시간은 몇 배가 난다.
몇 배인가? `atomic`이 정확한 값을 내는 대가로 하드웨어에게 무엇을 요구하는지
생각해 보라. 같은 칸을 여러 스레드가 동시에 1 늘리려 할 때, 하드웨어가
정확성을 지키려면 그 스레드들을 어떻게 처리해야 하는가?

**3.** `--skewed`로 바꾸면 세 버전의 시간이 각각 어떻게 움직이는가?
4절 표의 "몇 배" 열에서 **시간이 가장 크게 늘어난 버전**을 고르고,
왜 그 버전이 분포에 가장 민감한지 설명하라.
줄어든 버전이 있다면 그것도 그대로 적는다.

- 균등 분포에서 한 칸을 동시에 노리는 스레드는 평균 몇 개인가?
  칸이 256개이고 원소가 `N`개일 때로 계산해 보라
- 치우침 분포에서는 그 수가 어떻게 되는가?
- `private`에서 한 칸을 두고 경쟁하는 범위는 어디까지인가?
  전역 `bins`를 두고 경쟁하는 것과 무엇이 다른가?
