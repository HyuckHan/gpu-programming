# lab10 — 히스토그램과 데이터 경쟁

**목표:** 데이터 경쟁이 실제로 어떤 결과를 내는지 관찰하고, atomic 연산과 privatization의 비용을 측정한다.

`histogram.cu` 하나에 커널 세 개가 들어 있다. 첫 번째는 완성 상태로 제공되고,
나머지 두 개를 차례로 채운다.

## 1. 먼저 그냥 돌려 본다

```
make
./histogram
```

`race` 커널은 슬라이드 3의 코드 그대로다. `bins[b]`를 그냥 1 늘린다.
합계가 몇으로 나오는지 보라. 정상이라면 `N`과 같아야 한다.

**세 번 반복 실행해서 표를 채운다.**

## 빌드와 실행

```
make            # histogram 을 빌드한다
make run        # ./histogram 67108864 과 같다
make skewed     # ./histogram 67108864 --skewed 과 같다
make test       # verify.py 로 자체 점검한다
make clean
make help
```

인자는 `./histogram <N> [--skewed]` 형태이고, 생략하면 `67108864`(1<<26)이다.
`NUM_BINS`는 256으로 고정이다. 공유 메모리로 1KB뿐이라 여유가 충분하다.

## 검증

```
make test
```

`verify.py`는 **private 커널만** 판정한다. `race`는 틀리는 것이 정상이라
판정 대상이 아니다. 프로그램 자체는 256개 칸을 CPU 참조와 정수 정확일치로
비교한다. 히스토그램은 정수 세기라 허용오차가 없다. 한 칸이라도 다르면 실패다.

합계는 판정과 별개로 항상 찍힌다. 어느 칸이 틀렸는지보다 합계가 먼저 눈에 들어온다.

## 토론 문제

**1.** `race` 버전의 합계가 `N`보다 작게 나온다. 그리고 실행할 때마다 다르다.
사라진 증가 연산은 어디로 갔는가? 두 스레드가 같은 칸을 동시에 1 늘리려 할 때
무슨 일이 일어나는지, 읽고-더하고-쓰는 세 단계로 나눠서 적어 보라.

**2.** `atomic`은 정확하지만 느리다. 무엇 때문에 느린가?
`race`와 `atomic`의 코드 차이는 한 줄뿐인데 시간은 몇 배가 난다.
그 한 줄이 하드웨어에게 무엇을 요구하는지 생각해 보라.

**3.** `--skewed`로 바꾸면 `atomic`은 느려지는데 `private`는 거의 그대로다.
왜 이런 차이가 생기는가? 각 버전에서 **같은 칸을 동시에 노리는 스레드가
몇 개나 되는지**를 세어 보면 실마리가 잡힌다.
`private`에서 한 칸을 두고 경쟁하는 범위는 어디까지인가?
