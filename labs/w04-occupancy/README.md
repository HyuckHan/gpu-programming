# 4주차 실습 — 워프와 Occupancy

**목표:** 블록 크기가 SM 점유율(occupancy)과 성능에 어떻게 연결되는지 직접 측정하고,
워프 분기(divergence)가 실행 시간에 미치는 영향을 확인한다.

이번 주는 새 커널을 거의 만들지 않는다. **2주차에 완성한 `vecadd`를 그대로 쓴다.**

---

## 0. 준비

```bash
make
```

`vecadd`와 `divergence` 두 개가 빌드된다.
`vecadd.cu`는 2주차에 여러분이 채운 것과 같은 파일이다.

빌드가 안 되면 먼저 손을 들 것. 여기서 막히면 오늘 실습을 못 한다.

## 2. 손으로 먼저 계산한다 (15분)

**실행하기 전에** 아래 표의 "예상" 칸을 채운다. 계산식은 다음과 같다.

```
SM당 활성 블록 수 = min( SM당 최대 블록 수,  SM당 최대 스레드 수 / blockDim )
SM당 활성 스레드 수 = SM당 활성 블록 수 × blockDim
Occupancy = SM당 활성 스레드 수 / SM당 최대 스레드 수
```

나눗셈은 내림한다. 블록은 쪼개서 올릴 수 없다.

| blockDim | 활성 블록(예상) | 활성 스레드(예상) | Occupancy(예상) |
|---|---|---|---|
| 32 | | | |
| 64 | | | |
| 128 | | | |
| 256 | | | |
| 512 | | | |
| 1024 | | | |

채운 다음 확인한다.

```bash
for b in 32 64 128 256 512 1024; do ./vecadd 9999999 $b; done
```

**예상과 실제가 다른 칸에 표시하고, 왜 틀렸는지 한 줄씩 적는다.**
틀리는 것이 정상이다. 어디서 틀렸는지가 오늘 배우는 내용이다.

## 4. 워프 분기 실험 (15분)

`divergence`는 같은 양의 연산을 두 가지 방식으로 나눠서 수행한다.

```bash
./divergence
```

- **분기 있음** — 스레드 번호가 짝수냐 홀수냐로 갈린다.
  같은 워프 안에서 갈라진다.
- **분기 없음** — 워프 번호가 짝수냐 홀수냐로 갈린다.
  워프 안의 32개 스레드는 모두 같은 쪽으로 간다.

| 버전 | 시간(ms) |
|---|---|
| 분기 있음 | |
| 분기 없음 | |
| 비율 | |

두 커널의 소스를 열어 **어느 줄이 다른지** 확인한다. 한 줄이다.

## 5. 토론 문제

답을 적어서 제출한다. 정답을 검색하지 말고 위에서 측정한 숫자로 설명할 것.

1. blockDim=1024일 때 occupancy가 100%가 되지 못한다. 왜인가?

2. occupancy는 blockDim에 따라 크게 달라지는데 커널 시간은 그만큼 달라지지
   않는다. `vecadd`가 어떤 종류의 커널이기 때문인가?

3. 연산량이 똑같은데 분기 있는 버전이 더 느리다. GPU가 워프 단위로
   명령을 실행한다는 사실과 어떻게 연결되는가?
