# lab02 — 벡터 덧셈

**목표:** GPU에서 벡터 덧셈을 끝까지 동작시키고, 전체 시간에서 커널이 차지하는 몫이 얼마나 되는지 눈으로 확인한다.

## 첫 실행 확인 — 오늘의 최소 목표

```
make
./vecadd
```

**`검증: PASS`가 뜨면 성공이다. 여기까지가 오늘 반드시 도달해야 하는 지점이다.**

지금 그대로 돌리면 실패한다. `vecadd.cu`에 채워야 할 곳이 두 군데 있기 때문이다.
아래 순서를 따라가면 된다. 뒤쪽의 스윕 표와 토론 문제는 그다음이다.

## 실습 순서

## 1. 일단 돌려 본다

```
make
./vecadd
```

`검증: FAIL`이 나온다. 정상이다. 아직 `// TODO:`를 안 채웠다.
어느 인덱스부터 틀렸는지 적어 두라.

## 2. 경계 검사 없는 버전을 관찰한다

```
make vecadd_naive
./vecadd_naive
```

`vecadd_naive.cu`는 슬라이드 18의 커널과 슬라이드 12의 실행 구성을 그대로 옮긴
것이다. 두 가지를 확인하라.

**(가)** `검증: FAIL`과 함께 첫 불일치 인덱스가 나온다.
그 숫자가 왜 하필 그 값인지 계산해 보라. `N`, `numThreadsPerBlock`,
그리고 `numBlocks`를 구하는 식을 나란히 놓으면 보인다.

**(나)** `vecadd_naive.cu`에서 `numBlocks`를 구하는 줄을 **올림으로 고쳐서**
다시 빌드하고 돌려 보라. 검증 결과가 어떻게 바뀌는가?
그다음 이렇게 돌려 보라.

```
compute-sanitizer ./vecadd_naive 999999 256
```

`compute-sanitizer`는 CUDA 툴킷에 함께 들어 있다. **따로 설치할 필요가 없다.**
검증 결과와 `compute-sanitizer`의 결과를 함께 적어 두라.
관찰이 끝나면 고친 줄은 원래대로 되돌려 놓는다.

## 3. TODO를 채운다

## 빌드와 실행

```
make               # vecadd 만 빌드한다
make vecadd_naive  # 관찰용은 2단계에서 직접 빌드한다
make run           # ./vecadd 9999999 256 과 같다
make clean
make help          # 쓸 수 있는 명령과 인자를 모두 보여준다
```

인자는 `./vecadd <N> <blockDim>` 형태이고, 생략하면 `9999999 256`이다.
`make run N=1000000 B=512` 처럼 Makefile 변수로 넘겨도 된다.

> 기본 `N`이 홀수인 것은 일부러 그렇게 둔 것이다. 어떤 `blockDim`으로도
> 나누어떨어지지 않으므로, 실행 구성을 잘못 잡으면 반드시 드러난다.
> `blockDim`은 32 이상 1024 이하의 32의 배수만 받는다.

## 시간 측정

프로그램은 세 구간을 따로 잰다. 아래 숫자는 출력의 모양을 보여 주는 예시일 뿐이다.
PC 마다 다르게 나오니 그대로 나오기를 기대하지 말 것.

```
H2D 전송 :   12.028 ms
커널     :    0.507 ms
D2H 전송 :    5.913 ms
─────────────────────────────────────
전체     :   18.448 ms   (커널 비중 2.7%)
```

`커널 비중`이 이 랩의 핵심 숫자다. 토론 문제 1번에서 쓴다.

## blockDim 스윕

`./vecadd 9999999 <blockDim>`을 여섯 번 돌려 표를 채운다.
`SM당 활성 블록`과 `occupancy`는 프로그램이 실행 중인 GPU에 직접 물어 첫 줄에 찍는다.

| blockDim | SM당 활성 블록 | occupancy | 커널 ms | 전체 ms | 커널 비중 |
|---|---|---|---|---|---|
| 32 |  |  |  |  |  |
| 64 |  |  |  |  |  |
| 128 |  |  |  |  |  |
| 256 |  |  |  |  |  |
| 512 |  |  |  |  |  |
| 1024 |  |  |  |  |  |

## 검증

```
make test       # python3 verify.py 와 같다
```

`verify.py`가 빌드부터 다섯 가지 조합 실행까지 자동으로 돌린다.
나누어떨어지지 않는 `N`과 딱 떨어지는 `N`이 함께 들어 있다.
**제출 전에 반드시 통과시켜라.**

## 토론 문제

보고서에 답한다.

**1.** 전체 시간에서 커널이 차지하는 비중은 몇 %인가? 나머지는 무엇에 쓰였는가?
이 프로그램만 놓고 보면 GPU를 쓰는 것이 이득인가? 그렇다면/아니라면 왜인가?
어떤 조건이 갖춰져야 GPU를 쓰는 것이 이득이 되겠는가?

**2.** `blockDim`을 32에서 1024까지 바꾸면 occupancy는 눈에 띄게 변한다.
그런데 커널 시간은 그만큼 변하지 않는다. 왜인가?
이 커널이 원소 하나를 처리하기 위해 메모리에서 몇 바이트를 읽고 쓰는지,
그리고 계산은 몇 번 하는지 세어 보면 실마리가 잡힌다.
