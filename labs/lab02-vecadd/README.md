# lab02 — 벡터 덧셈

**목표:** GPU에서 벡터 덧셈을 끝까지 동작시키고, 실행 구성을 잘못 잡으면 무슨 일이
일어나는지 두 가지 방식으로 확인한다.

## 첫 실행 확인 — 오늘의 최소 목표

```
make
./vecadd
```

**출력이 나오면 성공이다. 여기까지가 오늘 반드시 도달해야 하는 지점이다.**

`검증: PASS`가 나온다. 그런데 **이 프로그램은 아직 틀렸다.**
`vecadd.cu`에 채워야 할 곳이 한 군데 남아 있다. 어디가 틀렸는지 찾는 것이
오늘 실습의 절반이다. 아래 순서를 따라간다.

## 실습 순서

## 1. 뒤쪽 원소가 계산되지 않는 버전 — 산수로 찾는다

```
make vecadd_naive
./vecadd_naive
```

`vecadd_naive.cu`는 슬라이드 18의 커널과 슬라이드 12의 실행 구성을 그대로 옮긴
것이다. 손댄 곳이 없다. 그런데 결과가 틀리다.

```
N = 9999999, blockDim = 256, numBlocks = 39062, 배열 3개 합계 114.4 MB

  첫 불일치: [9999872]  기대 0.871958  실제 0.000000
검증: FAIL
```

첫 줄의 `numBlocks`와 `blockDim`을 곱해 보라. 그 값이 첫 불일치 인덱스와
정확히 같을 것이다. 왜 그런지 보고서에 적는다.

- `numBlocks`를 구하는 식은 슬라이드 12에 있다. 그 식이 `N`을 `blockDim`으로
  나눈 몫이다. 정수 나눗셈이 나머지를 어떻게 하는가?
- 만들어진 스레드는 모두 몇 개인가? `N`보다 많은가 적은가?
- 계산되지 않은 원소는 몇 개인가?

**이 버그는 도구가 필요 없다.** 곱셈 한 번으로 찾을 수 있다.
계산되지 않은 원소는 `cudaMemset`이 넣어 둔 0으로 남아 있다.

## 2. 도구를 대 본다 — 아무것도 안 나온다

1단계의 프로그램에 `compute-sanitizer`를 씌워 보라.

```
compute-sanitizer ./vecadd_naive
```

`compute-sanitizer`는 CUDA 툴킷에 함께 들어 있다. **따로 설치할 필요가 없다.**
잘못된 메모리 접근을 잡아내는 도구다. 그런데 결과는 이렇다.

```
========= ERROR SUMMARY: 0 errors
```

**오류가 0건이다.** 검증은 FAIL 인데 도구는 아무 문제도 못 찾는다.
왜 그런지 생각해 보라. 이 커널이 배열 밖을 건드린 적이 있는가?
뒤쪽 원소는 잘못 계산된 것인가, 아니면 아예 계산되지 않은 것인가?

이 결과를 보고서에 적어 둔다. 3단계와 짝을 이룬다.

## 3. `./vecadd` 에 도구를 대 본다 — 이번에는 잡힌다

`vecadd.cu`는 `numBlocks`를 **올림**으로 구한다. 슬라이드 12와 다른 유일한
지점이고, 소스에 그렇게 주석이 붙어 있다. 그래서 1단계의 문제는 없다.

```
./vecadd
```

`검증: PASS`가 나온다. 첫 줄의 `numBlocks`에 `blockDim`을 곱해 보라.
이번에는 `N`보다 **크다.** 남는 스레드가 생겼다는 뜻이다.
그 스레드들은 무엇을 하고 있겠는가?

```
compute-sanitizer --print-limit 3 ./vecadd
```

```
========= Invalid __global__ read of size 4 bytes
=========     at vecadd_kernel(float *, float *, float *, int)+0x80
=========     by thread (192,0,0) in block (39062,0,0)
=========     Access to 0x50a825b00 is out of bounds
=========     and is 261 bytes after the nearest allocation at 0x508200000 of size 39999996 bytes
========= ERROR SUMMARY: 130 errors
```

주소값과 오류 건수는 실행할 때마다 다르다. 같은 명령을 두 번 돌리면
`130 errors` 였던 것이 `65 errors` 로 나오기도 한다. **0 이 아니라는 것이 요점이다.**
읽어야 하는 것은 그 옆의 정보다.

- **어느 블록의 몇 번 스레드인가.** `block`과 `thread` 번호로 `i`를 계산해 보라.
  그 `i`가 `N`보다 큰가?
- **`nearest allocation` 의 크기가 얼마인가.** 배열 하나가 몇 바이트여야 하는가.
  거기서 몇 바이트를 벗어났는가? 그 정도로 벗어났는데도 검증이 `PASS`였던 것과
  이어서 생각해 보라.
- `Invalid __global__ read` 인가 `write` 인가. 커널의 그 한 줄에서 읽기와 쓰기가
  각각 어디인가.

`--print-limit`을 주지 않으면 같은 오류가 수십 줄 반복된다.

> 도구를 씌워서 돌리면 오류가 잡힌 뒤에 프로그램이 `unknown error`로 끝난다.
> 잘못된 접근이 있으면 그 프로세스의 CUDA 상태가 망가지기 때문이다.
> 코드가 더 나빠진 것이 아니다. 도구 없이 그냥 돌리면 여전히 `PASS`가 나온다.

**2단계와 3단계 사이가 이 랩의 핵심이다.** 버그가 두 개 있었는데
증상도 진단 방법도 서로 달랐다. 한쪽은 검증이 잡고 도구는 놓쳤고,
다른 한쪽은 검증이 놓치고 도구가 잡았다.

## 빌드와 실행

```
make               # vecadd 만 빌드한다
make vecadd_naive  # 관찰용은 1단계에서 직접 빌드한다
make run           # ./vecadd 9999999 256 과 같다
make clean
make help          # 쓸 수 있는 명령과 인자를 모두 보여준다
```

인자는 `./vecadd <N> <blockDim>` 형태이고, 생략하면 `9999999 256`이다.
`make run N=1000000 B=512` 처럼 Makefile 변수로 넘겨도 된다.

> 기본 `N`이 홀수인 것은 일부러 그렇게 둔 것이다. 어떤 `blockDim`으로도
> 나누어떨어지지 않으므로, 실행 구성을 잘못 잡으면 반드시 드러난다.
> `blockDim`은 32 이상 1024 이하의 32의 배수만 받는다.

## 시간 측정

프로그램은 세 구간을 따로 잰다. 아래 숫자는 출력의 모양을 보여 주는 예시일 뿐이다.
PC 마다 다르게 나오니 그대로 나오기를 기대하지 말 것.

```
N = 9999999, blockDim = 256, numBlocks = 39063, 배열 3개 합계 114.4 MB

검증: PASS

H2D 전송 :    9.736 ms
커널     :    0.696 ms
D2H 전송 :    5.190 ms
─────────────────────────────────────
전체     :   15.622 ms   (커널 비중 4.5%)
```

`커널 비중`이 이 랩의 핵심 숫자다. 토론 문제 1번에서 쓴다.

## blockDim 스윕

`./vecadd 9999999 <blockDim>`을 여섯 번 돌려 표를 채운다.
`blockDim`을 바꾸면 `numBlocks`가 어떻게 따라 움직이는지 함께 본다.

| blockDim | numBlocks | numBlocks × blockDim | 커널 ms | 전체 ms | 커널 비중 |
|---|---|---|---|---|---|
| 32 |  |  |  |  |  |
| 64 |  |  |  |  |  |
| 128 |  |  |  |  |  |
| 256 |  |  |  |  |  |
| 512 |  |  |  |  |  |
| 1024 |  |  |  |  |  |

세 번째 열은 손으로 곱해 적는다. 여섯 줄 모두 `N`보다 커야 한다.
얼마나 큰지가 줄마다 다르다.

## 검증

```
make test       # python3 verify.py 와 같다
```

`verify.py`는 세 단계로 돌린다.

1. 빌드
2. 다섯 가지 `(N, blockDim)` 조합 실행 — 나누어떨어지지 않는 `N`과
   딱 떨어지는 `N`이 함께 들어 있다
3. `compute-sanitizer` 두 번 — **범위 밖 접근이 0건이어야 통과다**

3단계가 없으면 안 되는 이유는 3단계 실습에서 직접 봤다.
경계 검사를 빼먹은 커널도 2단계는 전부 통과한다.
**제출 전에 반드시 통과시켜라.**
