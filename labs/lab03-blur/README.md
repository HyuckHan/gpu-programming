# lab03 — blur와 경계 조건

**목표:** 경계 검사가 없는 커널이 어떻게 죽는지 보고, 원인을 **도구로** 찾아낸 뒤,
경계 조건을 직접 채워 고친다.

## 실습 순서

## 1. 경계 검사 없는 버전을 빌드해서 돌려 본다

```
make blur_naive
./blur_naive
```

`blur_naive.cu`는 슬라이드 17의 커널을 그대로 옮긴 것이다.

**결과 이미지가 가장자리만 이상하게 나오는 것이 아니다. 커널이 아예 죽는다.**
GPU 출력 자리에 이런 줄이 나온다.

```
GPU 출력: 없음 — 커널이 끝까지 실행되지 못했다
  an illegal memory access was encountered
```

여기서 알 수 있는 것은 "잘못된 메모리 접근이 있었다"는 사실뿐이다.
어느 줄인지, 어느 스레드인지, 어떤 주소인지는 알려 주지 않는다.
**이 실습의 과제는 그것을 찾아내는 것이다.** 짐작으로 소스를 읽지 말고 도구를 쓴다.

> 커널이 죽으면 그 프로세스의 CUDA 컨텍스트가 망가진다. 이후 실행에서
> `unknown error` 같은 엉뚱한 메시지가 나올 수 있다. 코드가 더 나빠진 것이
> 아니므로 그럴 때는 그냥 다시 실행하면 된다.

## 2. `compute-sanitizer`로 원인을 찾는다 — 주된 도구다

```
compute-sanitizer --print-limit 5 ./blur_naive 256 256 1
```

lab02 에서 쓴 그 도구다. 이번에는 두 가지가 다르다.
첫째, lab02 의 커널은 두 줄이라 어디가 문제인지 뻔했지만 이 커널은 스무 줄이다.
둘째, lab02 의 프로그램은 끝까지 돌았지만 이번에는 커널이 죽는다.

그래서 **어느 소스 줄에서** 일어났는지까지 받아 본다.

```
========= Invalid __global__ read of size 1 bytes
=========     at blur_kernel(...)+0x2b0 in .../blur_naive.cu:23
=========     Address 0x6085ffeff is out of bounds
```

`blur_naive.cu:23`이 범인이다. 그 줄을 열어 무엇을 읽으려 했는지 보라.
Makefile이 `-lineinfo`로 빌드하기 때문에 줄 번호가 나온다. 이 플래그가 없으면
함수 이름까지만 나오고 줄 번호는 나오지 않는다. lab02 의 출력에 줄 번호가
없었던 것이 그래서다. 같은 플래그를 lab08 에서 `ncu` 때문에 다시 쓴다.

`--print-limit`을 주지 않으면 같은 오류가 수백 줄 반복된다.
이미지를 작게(`256 256 1`) 잡는 것도 같은 이유다.

보고서에는 다음을 적는다.

- 몇 번째 줄인가. 그 줄의 어떤 식이 문제인가
- 그 줄에서 읽으려는 `inRow`, `inCol`이 어떤 값일 때 이미지 밖으로 나가는가
- 이미지의 어느 위치를 담당하는 스레드가 그런 값을 만드는가

## 3. `blur.cu`의 TODO를 채운다

```
make blur

```

`blur.cu`는 슬라이드 19를 기반으로 한다. 커널 시그니처, 바깥 `if`, 이중 루프,
마지막 나눗셈은 이미 완성되어 있다. **안쪽 루프 본체만** 채우면 된다.
슬라이드 19를 그대로 옮기면 된다.

## 빌드와 실행

```
make            # blur 만 빌드한다
make blur_naive # 관찰용은 1단계에서 직접 빌드한다
make run        # ./blur 512 512 1 과 같다
make clean
make help       # 쓸 수 있는 명령과 인자를 모두 보여준다
```

인자는 `./blur <width> <height> <BLUR_SIZE>` 형태이고, 생략하면 `512 512 1`이다.
`make run W=256 H=256 B=3` 처럼 Makefile 변수로 넘겨도 된다.
nvcc 플래그는 Makefile이 관리하므로 직접 칠 일은 없다.

> 슬라이드에서 `BLUR_SIZE`는 `#define` 상수지만, 실습에서는 실행할 때 바꿔 볼 수
> 있도록 커널 매개변수로 옮겼다. 커널 안에서 쓰는 방식은 슬라이드와 같다.

## 입력 이미지

작업 디렉터리에 `input.pgm`(PGM P5 형식)이 있으면 그것을 읽고, 없으면 16픽셀 폭의
사선 무늬를 `width x height` 크기로 만들어 쓴다. `input.pgm`이 있으면 크기 인자는
무시된다. 결과는 항상 `out.pgm`으로 저장된다.

다른 그림으로 시험해 보고 싶으면 만들어 쓰면 된다:

```
python3 make_input.py            # 512x512 input.pgm 을 만든다
python3 make_input.py 300 200
```

무늬가 네 변에 모두 걸치도록 그린다. 경계 처리 버그는 테두리 근처만 바꾸므로,
그 자리가 평평한 색이면 버그가 있어도 드러나지 않기 때문이다.
본인 사진을 쓰려면 **8비트 회색조 P5**로 변환해야 한다
(`convert photo.jpg -colorspace Gray -depth 8 input.pgm`).
16비트나 P2(ASCII) 형식은 읽지 못하며, 그 경우 경고를 찍고 합성 이미지로 넘어간다.

**`verify.py`를 돌릴 때는 `input.pgm`을 옮겨 두어라.** 크기 인자가 무시되면
점검이 성립하지 않으므로 스크립트가 실행을 거부한다.

`blur`와 `blur_naive`가 같은 `out.pgm`에 쓰므로, 나중에 실행한 쪽이 덮어쓴다.
둘을 나란히 비교하려면 중간에 파일 이름을 바꿔 두어라.

## 검증

```
make test       # python3 verify.py 와 같다
```

`verify.py`가 빌드부터 다섯 가지 조합 실행까지 자동으로 돌린다. 정사각이 아닌 크기,
블록(16x16)으로 나누어떨어지지 않는 크기, 그리고 창이 이미지보다 커서 모든 픽셀이
잘려 나가는 경우가 함께 들어 있다. **제출 전에 반드시 통과시켜라.**

프로그램은 GPU 결과를 CPU 참조 구현과 대조한다. 정수 연산이므로 허용오차가 없다.
**한 바이트라도 다르면 실패다.** 불일치 위치는 1차원 인덱스로 나오며,
행 = i / width, 열 = i % width 로 읽는다.

`blur_naive`는 이 검증을 통과하지 못한다. 그것이 정상이다.
커널 자체가 죽어 GPU 출력이 아예 없으므로 `검증: FAIL`로 끝난다.

## 터미널 미리보기

두 프로그램 모두 입력, GPU 출력, CPU 참조의 좌상단 8x8 픽셀값을 정수로 찍는다.
이미지 뷰어 없이 이 숫자만 보고도 결과가 맞는지 가늠할 수 있다.
정상이라면 GPU 출력과 CPU 참조의 숫자가 완전히 같다.
`blur_naive`는 커널이 죽어 GPU 출력 자리가 통째로 비어 있다.

## 제출물

- `blur.cu` — 안쪽 루프를 채운 것 (파일명 그대로)
- `report.md`
  - 1단계에서 `./blur_naive`가 어떻게 끝났는지. 그 메시지만으로 알 수 있는 것과
    알 수 없는 것을 각각 적어라
  - 2단계 `compute-sanitizer` 출력에서 읽어낸 것:
    어느 줄인가, 어떤 접근인가, 주소가 왜 범위 밖인가
  - 왜 하필 그 스레드에서 문제가 생기는가 (`inRow`, `inCol`의 값을 들어 설명)
  - `BLUR_SIZE`를 1, 4, 16으로 바꾸면 잘못된 접근의 범위가 어떻게 달라지는가.
    `compute-sanitizer`의 `ERROR SUMMARY` 개수를 함께 적으면 좋다

**제출: 필수**

전체 12개 실습 중 10개 이상 제출해야 P 를 받을 수 있다.
